Design guide

Docs design guide

How the manual looks on dozersandbox.com/docs. This page is built with the rules it describes, and every specimen below uses real text from the manual.

Source: DESIGN.md holds the rules in words, this page shows them. The CSS is docs/docs.css, on top of site.css.

Principles#

  1. The same site. The docs use the home page's header, footer, black-on-white, hairlines, pills and hard black shadow, and the single accent #ffd60a with its tints. A reader should not notice a seam when they click Docs.
  2. Built for reading and scanning. One column at 70 characters, 17px text on a 1.65 line height, strong headings, and a sidebar and an on-page contents so nobody scrolls to find a section.
  3. Fast. Static HTML and two stylesheets. The page reads fully with JavaScript off; the only script is a 20-line progressive enhancement (the Copy button and the current-section marker). No web fonts, no third-party scripts, no images beyond the manual's own screenshots.
  4. Accessible. Body text is black on white (21:1; the lightest text is #555 at 7.5:1). Focus is a 3px black ring. There is a skip link, one h1 per page, headings never skip a level, and tables and code scroll in boxes that can take keyboard focus.
  5. Works at 390px. Nothing makes the page scroll sideways: wide things scroll inside their own box. The sidebar becomes a Chapters button.

Layout#

The header is the home page's (.nav), with Docs carrying aria-current="page" and the footer is the home page's footer. Below the header the page is a three-column grid, .dlayout.

Sidebar#

The chapter list, grouped as the manual's contents are (Start here, Install and set up, Using Dozer, Files and tools, Looking after sandboxes, Reference, Experimental). The current chapter has the accent tint, bold text and a 3px black bar on its left; hover is the soft tint. Group headings are 12px small caps. It is on the left of this page.

On this page#

Every h2 and h3 of the article, in grey with a hairline on the left. The section being read is black and bold with a 3px bar (set by the small script; without it, nothing is marked and nothing breaks). A chapter with fewer than three headings omits it.

Chapter header#

Breadcrumb (Docs › Chapter title), then an accent pill with the chapter number, the h1, a one-line summary in the secondary grey, and a hairline underneath. The summary is the manual page's first paragraph, cut at its first sentence.

The contents page#

/docs/ has no sidebar chapter marked. It is the manual's README: the introduction, the four read first chapters as a numbered list, then every chapter as a card (number in mono, title, the read it when you want to… line), then the conventions.

Typography#

The site's system stack (-apple-system, BlinkMacSystemFont, "SF Pro…", Helvetica Neue…) and its mono stack (ui-monospace, "SF Mono", Menlo). Nothing is downloaded. Headings are tight like the home page's, but a good deal smaller.

h1 · 34–46pxTerminals and sessions
h2 · 28pxIn the terminal
h3 · 21pxRestarting or ending a session
h4 · 17px boldSeveral people or windows can view one session
body · 17px/1.65Sessions live in the sandbox, not in your terminal: you attach to one, detach, come back later from another terminal or the browser.
table · 15pxThe default for a cell; secondary captions are 14px, labels 12px.

Rules. Measure: 70ch. Paragraph spacing: 1.1em (no indent). An h2 has a hairline above it and 2.2em of space; h3 and h4 have no rule. Text is left-aligned, never justified, and uses text-wrap: balance on headings. Bold lead-ins (Concepts.) stay bold. Links to other chapters are plain links; there is no visited colour.

Components#

Inline code and keys#

Inline code is 0.88em mono, black on the soft accent tint (--tint-soft), a 5px radius, wrapping anywhere so a long setting key never forces a sideways scroll. Example: doz up, sandbox.clipboard, ~/.config/dozer-sandbox/doz.toml. Keys use <kbd>: white, black border with a heavier bottom edge. Press Ctrl-] twice to leave the sandbox, or Esc to go back. The manual writes keys in bold (Ctrl-]); the converter turns bold text that names a key into <kbd> where it is clearly one, and leaves the rest bold.

Code blocks#

A white panel with a 1px black border, 14px radius and the site's hard shadow (0 4px 0 #000). A caption bar on the soft tint holds the language (sh, text, yaml, toml; lower case) and, when JavaScript runs, a Copy button. Text is 14.5px mono at 1.65 and never wraps: a long line scrolls inside the block (the block is keyboard-focusable). There is no syntax colouring; the only exception is a shell comment, which is grey #555. Copy copies the text with the comments left in, as the reader sees it. A literal $ prompt is not selected. Fences without a language show text.

ASCII diagrams and terminal captures are text blocks with the same frame, with line height 1.3 so box-drawing characters join up (.code.diagram).

The one Mermaid diagram (chapter 5's state diagram) is rendered to an SVG at build time, in black strokes with accent-filled states, and shown as a figure; the source stays available in a <details> under it. No Mermaid library is ever shipped to the browser.

Tables#

Every table is wrapped in .tablewrap: a 1px black border, 14px radius, scrolling sideways inside itself (tabindex="0", role="region" and an aria-label from the heading above it). The header row is the stronger accent tint (--tint) with a black rule beneath it; body rows have a grey hairline and every other row a 2.5% black wash. The first column is sticky and bold, so a row keeps its name while the rest scrolls. A table with five or more columns gets .wide (a minimum width of 860px). Cell text is 15px; code in a cell does not wrap.

Blockquotes and callouts#

The manual uses blockquotes three ways, and the converter tells them apart so each gets the right look.

Notes and tips are a blockquote that starts with a bold lead-in. They get a 4px black rule on the left, no fill, and text at body size.

Detach, don't quit. Press Ctrl-] twice to leave the sandbox (once opens a small menu at the bottom: d detach · n next · p prev · s sessions · Esc back). The agent keeps running, and doz up brings you straight back to it.

Warnings are the blockquotes whose lead-in says something must not be relied on (A convenience, not a security boundary, Not in public releases, Experimental). They are the one place the accent is used as a panel: the stronger tint, a 1px black border, 14px radius and a black Warning pill. The converter holds a short list of lead-ins that mean warning; anything else with a bold lead-in is a note.

A convenience, not a security boundary. The rules keep an agent from stumbling into files. Root in the sandbox — and the agent has sudo by default — can get around them. Anything that must not reach the sandbox at all belongs outside the shared folder (or in an isolated sandbox); see the Security model.

Examples are a blockquote with no bold lead-in: a prompt to paste, or output to expect. They are mono on the soft tint with a 1px black border and a small Example label.

where are you running, and where is /workspace on my Mac?

Lists and numbered steps#

Bullets are black discs; numbers are bold, tabular. Items are spaced 0.4em apart and may hold paragraphs, code blocks and nested lists, which are indented 1.5em. The numbered Where a value comes from list from the settings reference:

  1. a command-line flag (for the few settings that have one — --store, --progress, doz create --cpus, …);
  2. its environment variable (DOZ_STORE, DOZ_PROGRESS, DOZ_HOST_IDLE);
  3. the file;
  4. the default.
  • Several people or windows can view one session. What's typed in either shows in both.
  • The screen is kept inside the sandbox, so attaching from anywhere shows the current screen at once.

Links and heading anchors#

Links are black, underlined (1px, 3px offset), and on hover get the accent as a highlight with a thicker underline: there is no blue and no visited colour. A link off the site, such as Homebrew, ends in a small arrow. A link to another chapter is the chapter's .html page, such as Signing in from a sandbox; one into a section is chapter.html#section and the target flashes the soft tint for a second.

Every h2, h3 and h4 has an id (the slug of its text, deduplicated within the page, exactly as GitHub makes them so the manual's existing #fragment links keep working) and a # after it that appears on hover or focus, and always on touch screens at 45% grey. It is a link: click it and copy the address. Hover over any heading on this page to see it.

Images and figures#

A screenshot is framed like the home page's: 1px black border, 14px radius, the hard shadow, white behind it, never wider than the column, with its width and height attributes set so the page does not jump. The caption is the Markdown alt text, in 14px grey underneath. Images are copied with the pages and referenced as /docs/images/…, with the manual's alt text kept as the alt.

Colour#

Black, white, greys, and one accent. No other hue appears: no blue links, no red warnings, no green notes, no syntax colours. The accent is #ffd60a; the colour picker on the home page is local to that page and is not loaded in the docs.

  • #fffPage, panels, code blocks, table body
  • #000Text, borders, shadows, the focus ring, the Warning pill
  • --ink-2 #2b2b2dSummaries, captions, sidebar group names
  • #555 (7.5:1)Shell comments, heading anchors; the lightest text
  • --hairRow lines, h2 rules, the contents rail
  • --accentChapter pill, link hover, button hover, Copy done
  • --tint (55%)Current chapter, table header, warning panel, card hover
  • --tint-soft (24%)Inline code, code caption bar, example quote, link target flash

Contrast is black on white, black on --tint and black on --tint-soft, all above 15:1. Grey text is only ever on white or the soft tint and is at least #555. Nothing is conveyed by colour alone (the current chapter also has a bar and bold weight).

URLs and structure#

The contents page is /docs/ (a docs/index.html). Each chapter is /docs/<slug>.html where the slug is the Markdown file name without its number and extension: 07-terminals-and-sessions.md becomes /docs/terminals-and-sessions.html. A URL never changes when chapters are renumbered. The chapter number is shown as the page's eyebrow (Chapter 7) and comes from the file name at build time. The site already serves .html files (timeline.html), so the docs follow that style.

Links in the Markdown are rewritten by the converter: 11-signing-in-from-a-sandbox.md#section becomes signing-in-from-a-sandbox.html#section; README.md becomes ./; an image images/x.png stays images/x.png (copied); links out of the manual (../CLI-USER-GUIDE.md) become absolute GitHub URLs. A link that resolves to nothing fails the build. tools/stamp.sh fingerprints docs.css and docs.js like site.css (?v=<hash>), in every page under docs/, and sitemap.xml gets every page. The home page's Docs link, the footer's Manual link and cli-commands.json's manual links change from GitHub to /docs/… at launch.

The build#

Described, not built. One script, tools/docs-build.py APP_CHECKOUT, in the style of tools/cli-data.py: it reads APP_CHECKOUT/docs/manual/*.md and writes docs/*.html and docs/images/, then you run tools/stamp.sh and commit. The pages are generated files, committed, like cli-commands.json; the manual in the app repo stays the single source of truth and no page is ever edited by hand.

  • The converter. Neither pandoc, cmark nor Python's markdown is installed here, so: a small, dependency-free Python converter for the subset the manual actually uses (ATX headings, paragraphs, bold, italic, inline code, links, images, bullet and numbered lists with nesting, pipe tables, blockquotes, fenced code, horizontal rules and a few HTML comments to drop), checked against every chapter. Fewer than 400 lines, no network, run with python3 -I. A single vendored MIT library (such as markdown-it-py) is the fallback if the subset grows, kept in tools/vendor/ and never served.
  • It fails loudly. Unknown syntax, a broken chapter link or fragment, a missing image, a table row with the wrong cell count, or a heading level that skips all stop the build with a file and line.
  • It checks its own output. It parses the pages back and compares word counts and every code block with the source, so a silently dropped paragraph cannot ship.
  • In sync with the app. The script takes the checkout path as cli-data.py does, records the app commit it built from in a comment at the top of docs/index.html, and the release steps run it with the version's checkout so the docs and the binary match; the app repo's existing docs check (every command, flag and setting in the manual exists) stays where it is.
  • Templates. The page frame (header, sidebar, footer) lives in tools/docs-template.html so a change to the nav is one edit. The sidebar groups and the previous/next order come from the manual's README.md contents list, so a new chapter appears when it is added there.
